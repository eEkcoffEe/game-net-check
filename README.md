GameNetCheck 1.5
Два режима: Wireshark + Process Monitor или Wireshark + NetLimiter.

УСТАНОВКА
Python 3.10+ с tkinter: https://www.python.org/downloads/windows/
Распакуйте весь архив в папку с заменой файлов. Запуск: Start.cmd.
Дополнительных pip-пакетов и прав администратора для анализа не нужно.

КАК СОБИРАТЬ
1. Закройте лишние приложения/вкладки. Выберите нужный EXE.
2. Начните запись Wireshark на активном адаптере ДО попытки подключения.
3. Одновременно записывайте Procmon или используйте историю NetLimiter.
4. Воспроизведите проблему, запишите время ошибки, остановите запись.
5. Сохраните PCAPNG и CSV за ТОТ ЖЕ сеанс. Не смешивайте разные попытки.
6. После исправления полезно записать успешную попытку для сравнения.

РЕЖИМ 1: PROCESS MONITOR CSV + WIRESHARK (предпочтительный)
Настройка Process Monitor перед записью:
1. Запустите Procmon от администратора. Ctrl+E — остановить текущий сбор.
2. Ctrl+L (Filter): Process Name -> is -> имя.exe -> Include -> Add -> OK.
   Для THE FINALS: discovery-d.exe. Для Chrome: chrome.exe.
   Если приложение использует несколько EXE, добавьте нужные процессы.
3. На панели оставьте включённой только Show Network Activity.
   Отключите File System, Registry, Process/Thread и Profiling Activity.
4. Options -> Resolve Network Addresses: ВЫКЛЮЧИТЬ.
   Path должен содержать числовые IP и порты, например 192.168.10.185:50000 -> 202.14.113.136:7903.
5. Options -> Select Columns: включить ОБЕ колонки:
   - Date & Time — дата и время, например 14.11.2026 1:06:44;
   - Time of Day — точное время с долями секунды, например 1:06:44,2384243.
   Также оставить Process Name, PID, Operation, Path, Result, Detail.
   Нажать OK. Time of Day НЕ удалять: Date & Time в вашем экспорте округлён до секунд.
6. Ctrl+X — очистить старые события. Начать запись Wireshark и Ctrl+E в Procmon.
7. Повторить проблемное действие. После ошибки остановить обе записи.
8. File -> Save -> Events displayed using current filter -> CSV.
   Сохранить PCAPNG из Wireshark от ТОЙ ЖЕ попытки.

В GameNetCheck:
- выберите режим, PCAPNG, CSV, EXE и локальный IPv4 компьютера;
- дата читается из Date & Time, точное время — из Time of Day;
- часовой пояс автоматически берётся с компьютера анализа с учётом даты;
- вопросов о дате/поясе при новом формате CSV нет;
- старые CSV без Date & Time по-прежнему требуют дату первого сетевого события.
  В таком случае предлагается локальная дата начала PCAP — её нужно проверить.

ВАЖНО ПРО ЧАСОВОЙ ПОЯС
Procmon экспортирует отображаемое время. Анализируйте на том же ПК/в том же
часовом поясе, где экспортировали CSV. Если CSV экспортирован в другом поясе,
задайте --utc-offset, например --utc-offset 5. В отчёте явно указано, что
использован системный пояс, либо заданное смещение. CSV не содержит UTC-смещения.
Поддерживаются DD.MM.YYYY HH:MM:SS и YYYY-MM-DD HH:MM:SS в Date & Time.
Другие/неоднозначные форматы не угадываются: строки отмечаются как пропущенные.
Если Time of Day отсутствует, используется Date & Time с предупреждением
о снижении точности. Противоречивые значения двух колонок пропускаются.
Сопоставление: TCP/UDP + локальный IP/порт + удалённый IP/порт + время.
Окно по умолчанию ±2 секунды вокруг каждого события Procmon.
Это корреляция потока, не идентификация каждого пакета. Один вызов Procmon
не обязан соответствовать одному пакету. Статистика сопоставленной строки
считает только пакеты в объединении окон событий. Полное число пакетов потока
также показано; часть пакетов вне окон не приписывается процессу.
Несколько процессов/PID с совпадением для одного tuple -> неоднозначно:
такая строка видна, но в правила не попадает. В длинных записях PID могут повторяться.
Если часы или файлы не совпадают, отчёт предупреждает. Автосдвига часов нет.
Переход времени через полночь поддерживается. CSV должен быть в порядке времени.

РЕЖИМ 2: WIRESHARK + NETLIMITER CSV
Экспортируйте свежую историю нужного приложения, желательно за время попытки.
Поддерживаются русские экспорты истории с колонкой порта и без неё.
Сопоставление ТОЛЬКО ПО IP. PID, протокол, локальный порт и время истории
не используются. Это слабая связь: один IP может использоваться разными EXE.
Если IP встречается у нескольких приложений в предоставленном CSV, строка
неоднозначна и исключается из правил. Другие приложения, отсутствующие в CSV,
по-прежнему могут использовать тот же IP — такая неоднозначность не выявляется.
Все счётчики пакетов берутся из Wireshark, не из байтов NetLimiter.

ЧТО В ОТЧЁТЕ
Главная страница report.html показывает:
- приложение и интервал записи;
- краткую сводку: сколько соединений/событий проанализировано и сколько требуют внимания;
- одну основную таблицу «Приложение | Домен / IP | Что обнаружено | Что проверить».
  Повторяющиеся однотипные наблюдения объединяются с указанием числа повторов.

Технические разделы вынесены в раскрывающиеся блоки:
- «Все соединения»;
- «DNS»;
- «Несопоставленные события»;
- «Технические подробности» (порты, PID, счётчики пакетов, время, качество сопоставления, RDAP/ASN, источники имён и т. п.).

Критичные предупреждения о качестве данных остаются на виду (например, CSV и PCAP не пересекаются по времени или нет сопоставленных соединений).
Если подозрительных ситуаций нет, отчёт пишет: «Явных признаков сбоя не найдено. Это не подтверждает доступность всех ресурсов».

Полные данные сохраняются в connections.csv, candidates.csv, session.json и др.

Как интерпретируются наблюдения (TCP/UDP):
- TCP: отдельно отмечаются попытки подключения без ответа, SYN без наблюдаемого SYN/ACK/RST, случай «соединение установлено, но после отправки данных дальнейшего прогресса не видно», полученный TCP RST, а также отправленный TLS ClientHello без наблюдаемого ответа сервера после него.
- Двусторонний обмен (TCP/UDP) фиксируется как наблюдение; успешность операции приложения по этому факту не утверждается.
- UDP без ответа отмечается как наблюдение и сам по себе не считается сбоем/блокировкой.
- RST и повторные передачи — наблюдаемые симптомы, не автоматическое доказательство блокировки.
- В основной таблице показываются наблюдаемые факты и что стоит проверить; найденные адреса не называются «заблокированными» без подтверждения.

Procmon и PCAP:
- Результат строится по обоим источникам. Ошибки Procmon (Result != SUCCESS) сохраняются в отчёте даже без пакетов в окне сопоставления: отдельно отмечается «пакетов 5-tuple в PCAP не найдено» и «пакеты есть, но не попали в окно сопоставления ±допуск».
- Отсутствие пакетов объясняется осторожно: возможны локальный отказ, другой интерфейс, неполный захват или несовпадение записей.
- По возможности независимые повторные попытки разделяются (по событиям/разрывам во времени), а не сводятся в один итог.
- Неоднозначное сопоставление (несколько процессов/PID на один 5-tuple) показывается отдельно и не попадает в кандидаты/правила.

NetLimiter:
- Поддержка режима сохранена; сопоставление слабое и выполняется только по IP. Порт, протокол, PID, время и отдельные попытки из NetLimiter не подтверждаются; принадлежность одному приложению по IP не доказывается.

DNS, имена и сети:
- Сбои DNS в PCAP: отрицательные DNS-ответы и запросы без ответа в записи (отдельно, не привязано к процессу). Отсутствие ответа в захвате не доказывает блокировку.
- При онлайн-анализе DNS-ошибки перепроверяются у DNS-сервера из PCAP и через Google/Cloudflare DoH; `--offline` отключает проверки.
- Fake-IP 198.18.x.x показываются с пояснением: для проверки дальнейшего подключения нужен журнал прокси/Podkop.
- PTR и владелец сети RDAP/BGP не выдаются за домен, запрошенный приложением; домен/источник имени показываются отдельно. Диапазоны/IP не расширяются автоматически.

РЕЗУЛЬТАТ — новая папка рядом с PCAP
report.html — отчёт в браузере.
connections.csv — все строки с совпадениями и без них, включая Домен/имя и источник.
candidates.csv — только кандидаты, включая домен/имя и источник.
name-lookups.json — результаты обратного DNS PTR, если включена интернет-проверка.
podkop-candidates.txt — кандидаты /32 для ручной проверки.
networks.json — интернет-сведения, если включены.
session.json — параметры пары файлов, часовой пояс, даты, допуск, предупреждения
и обнаруженные DNS-сбои.
Сайты внутри одного процесса браузера не разделяются. Закрывайте лишние вкладки.

ИНТЕРНЕТ
Запрашиваются до 20 уникальных публичных IP из сопоставленных кандидатов.
Реестрам RDAP/RIPEstat отправляются только IP. DNS-перепроверка отправляет
имя и тип запроса Google и Cloudflare; сами PCAP, CSV и имя EXE не отправляются.
Для кандидатов без найденного имени также отправляется обратный DNS-запрос
по IP в Google Public DNS (DoH JSON API). --offline отключает и эти запросы.
Кэш 24 часа для IP, 7 дней для IANA. Ошибки сервисов сохраняются в отчёте;
основной анализ продолжает работу. Кэш ошибок тоже хранится 24 часа.
Для повторного запроса удалите ip-*.json из %LOCALAPPDATA%\GameNetCheck\cache.
Флаг --offline отключает интернет. Нет изменений роутера или сетевых настроек.

КОМАНДНАЯ СТРОКА
Procmon:
py -3 scripts\GameNetCheck.py --pcap "C:\logs\match.pcapng" --csv "C:\logs\Procmon.csv" --mode procmon --process discovery-d.exe --local-ip 192.168.10.185
NetLimiter:
py -3 scripts\GameNetCheck.py --pcap "C:\logs\match.pcapng" --csv "C:\logs\NetLimiter.csv" --mode netlimiter --process discovery-d.exe --local-ip 192.168.10.185
Отдельный IP:
py -3 scripts\GameNetCheck.py --lookup-ip 202.14.113.136

--mode можно опустить: формат CSV определяется по заголовкам.
--process: точное имя EXE; без него — все приложения.
--tolerance 2: окно ±2 с (допустимо 0–30). Большое окно снижает точность.
--clock-shift 0: сколько секунд ДОБАВИТЬ к времени Procmon. Используйте только
при известной разнице часов; не подгоняйте несовместимые записи.
--no-open: не открывать браузер. --out: новая папка вывода.

ОГРАНИЧЕНИЯ И ПРОВЕРКА
PCAP: IPv4 TCP/UDP. DNS анализируется только для открытых DNS по UDP/TCP 53; DoH/DoT
и DNS-имена внутри зашифрованного трафика не видны. Онлайн-перепроверка DNS
отправляет имена запросов Google и Cloudflare; используйте `--offline`, чтобы
отключить её. IPv6, ICMP, фрагменты и расшифровка TLS не анализируются.
Multicast исключён. Имена извлекаются из открытого DNS и видимого TLS SNI. PML/EVTX не поддерживаются.
Захват на ПК не показывает фактический выход через КЗ; проверяйте лог Podkop.
Один tuple может повторно использоваться; делайте короткие записи одной попытки.
Не меняйте активный интерфейс/локальный IP посередине записи.
Отчёт показывает наблюдаемые факты и возможные причины; он не доказывает блокировку,
доступность всех ресурсов, принадлежность IP одному приложению (особенно в режиме NetLimiter)
или реальный маршрут через прокси. Настройки сети/прокси/маршрутизации не изменяются автоматически.

Проверено: три предоставленных PCAP с NetLimiter, числовой CSV Procmon,
предупреждение на реальных несовпадающих по времени файлах, а также синтетическая
совпадающая пара: IP/порты/протокол, время и часовой пояс, полночь, PID,
получение в обратном направлении, отсутствие ложного совпадения и RDAP-интеграция.
Дополнительно проверен предоставленный test.CSV с Date & Time: точные доли
секунды, системный пояс UTC+5, явное смещение, переход даты и конфликт колонок.
Добавлены воспроизводимые синтетические проверки (`py -3 tests\verify_report.py`):
несколько SYN без ответа; TCP ответил, но обмен завис после отправки данных;
успешный обмен с последующим RST; ошибка Procmon без пакетов в PCAP и случай
«пакеты есть, но вне окна сопоставления»; обычный UDP без обязательного ответа;
неоднозначное сопоставление; несовпадение времени CSV/PCAP; TLS ClientHello без
наблюдаемого ответа сервера. Проверено, что обычные соединения не помечаются как
требующие внимания и ошибки Procmon не исчезают; HTML сверён на случае с проблемами
и без них (явное сообщение об отсутствии явных признаков сбоя).
Реальная одновременная пара Procmon+PCAP от пользователя пока не предоставлена.
GUI и Start.cmd непосредственно на Windows в среде разработки не выполнялись.

ДОМЕН / ИМЯ — НОВОЕ В 1.5
В таблицах отчёта и CSV появились Domain, DomainSource, NameLookupStatus.
Приоритет:
1. TLS SNI из ClientHello того же TCP-потока. Имя привязано к IP и портам.
2. DNS A/CNAME в захвате ПК. Учитывается время и TTL ответа, но DNS не привязан
   к процессу: один адрес может иметь несколько имён. Показаны все найденные.
3. Имя хоста из CSV NetLimiter. Может быть обратным DNS, не исходным доменом.
4. Если имя отсутствует, для публичных IPv4-кандидатов (первые 20) проверяется
   PTR через Google Public DNS. Результат помечен как PTR — имя сервера.
Если PTR отсутствует или запрос завершился ошибкой, отчёт явно показывает это.
WHOIS/RDAP не используется для угадывания домена; он даёт сведения о сети.

TLS SNI не расшифровывается. При ECH наблюдаемое имя может быть внешним/прикрывающим.
QUIC, DoH, DoT и скрытое ECH-имя не разбираются. Если DNS/ClientHello были до
начала записи, имя может остаться неизвестным. Запускайте захват до подключения.
Разбираются открытые DNS по UDP/TCP 53 и начальный TLS ClientHello по TCP.
Сборка начального TCP-потока ограничена 64 KiB и 512 одновременно сохраняемыми
потоками; пропуски данных и сложные случаи сборки могут помешать извлечению имени.
Имена видны и для Fake-IP, если SNI/DNS присутствует, но это не раскрывает реальный
сервер назначения и не отменяет необходимость журнала Podkop.
В podkop-candidates.txt имя добавлено только комментарием к /32.
PTR не следует автоматически переносить в доменные правила: приложение могло
вообще не запрашивать это имя. Один IP может обслуживать множество доменов.
Интернет-PTR кэшируется 24 часа; сброс: ptr-*.json в папке cache.

Проверено: DNS A/CNAME и сжатые имена, защита от циклических DNS-указателей,
TLS SNI с разделёнными сегментами и повторной передачей, привязка к потоку,
TTL, PTR найден/отсутствует/ошибка, извлечение имён из трёх реальных PCAP,
регрессия сопоставления Procmon/NetLimiter. PTR 202.14.113.136 при проверке
не обнаружен — это не ошибка и не означает недоступность адреса.
